Stages proposed bank reconciliations so a human can review them in a
daily batch, and turns the ones nobody could guess into candidate
matching rules.

Each statement line the agent looks at lands in one of three buckets:

- **Confident** — applied immediately and flagged ``To Review`` in
  Odoo's own queue. Reconciliation is reversible, so a wrong confident
  match costs cleanup, not harm, and review becomes a sampling exercise
  rather than a bottleneck.
- **Needs a human** — nothing is written. The proposal is held as data
  and the entry is flagged ``anomaly``, which puts it in the same native
  "To Review" filter without touching a single value on the journal
  entry.
- **No idea** — recorded as an observation only, then clustered. A group
  of lines sharing a vendor prefix in one journal is one missing
  ``account.reconcile.model`` away from never needing an agent again, so
  the agent's own success metric is the share of work it stops having to
  do.

Two design points worth defending.

**The proposed action is data, not a half-written entry.** Nothing has
happened, so there is nothing to block — *"unapproved cannot take
effect"* is true by construction. The alternative, freezing fields on a
live record and maintaining a list of the ones that must stay writable,
is where approval frameworks usually become brittle.

**The agent queues work it cannot sign off.** Writing ``todo`` or
``anomaly`` needs no accounting rights, while ``reviewed`` requires
``account.group_account_user``. An agent below that group can therefore
fill the review queue and is structurally incapable of clearing it.
There is a test asserting exactly that, because the separation of duties
rests on it.

Usage
=====

Turn on **Accounting Firms mode** first — Settings → Accounting →
``set_to_review_documents``. Without it the review-state access checks
return immediately and the separation of duties is inert.

Give the agent its own user with ``base.group_user`` +
``account.group_account_invoice`` and **not**
``account.group_account_user``. Above that group, work it applies is
marked ``no_review`` and never enters the queue.

.. code:: python

   batch = env["ai.recon.batch"].create({"items_seen": len(lines)})
   env["ai.recon.proposal"].create({
       "batch_id": batch.id,
       "statement_line_id": line.id,
       "confidence": "high",          # or "medium" / "none"
       "account_id": expense.id,
       "partner_id": vendor.id,
       "rationale": "label matches the GitHub subscription pattern",
   })
   env["ai.recon.proposal"]._route(batch.proposal_ids)

Then ``batch.action_draft_rules()`` creates one **inactive**
``account.reconcile.model`` per cluster of unmatched lines. They change
nothing until somebody activates them, and the account is deliberately
left empty — choosing it is the judgement being asked for.

A warning about catch-all rules
-------------------------------

A reconcile model with no ``match_label``, ``match_amount`` or
``match_partner_ids`` becomes proposable purely by being set to
``auto_reconcile`` (``_compute_can_be_proposed``), and then matches
every line in its journals. Measured on a real database, one such rule
swept 714 of 754 lines into an "Uncategorized" account — technically
reconciled, substantively unclassified, and with the rule-discovery
signal destroyed. Keep catch-alls off while you are trying to learn what
rules you are missing.
