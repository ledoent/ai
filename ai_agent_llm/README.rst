Turns the durable runtime into an actual agent: instead of following a
plan written in advance, a model is given the goal and the agent's tool
schemas and chooses one action at a time, seeing each result before
deciding the next.

That difference is the point. A static plan has to guess every
identifier up front; a loop can look one up and then use it. It is also
where the risk is, so every control the runtime already had applies
unchanged — the model picks *which* tool, and gets no say in whether it
is allowed:

- **The allowlist is not advisory.** A tool the model names but the
  agent was not granted fails the run; an invented tool name does too.
- **Identity is unchanged.** Calls still run as the agent's user, so a
  tool the model chose but the user cannot use simply fails — and the
  failure goes into the transcript, so the model can see it and try
  something else.
- **Approval executes what the human saw.** After approval the pending
  call is replayed verbatim rather than asking the model again, which
  would let it substitute a different action for the one that was
  approved.
- **A step budget bounds the loop.** Without one, a model that keeps
  choosing tools runs until something external stops it, and on a
  production ERP that means an unbounded number of writes.

Providers sit behind a one-method interface (``_decide``) because every
vendor's tool-calling API is a different shape and none is a good thing
to build control flow around. A ``stub`` provider replays a scripted
sequence, which is what makes the loop assertable in CI with no network
and no API key.

API keys are read from an environment variable named by the provider
record, never stored in it — a credential in a database column ends up
in every backup, duplicate and support export of that database.

Usage
=====

.. code:: python

   provider = env["ai.agent.provider"].create({
       "name": "Claude",
       "kind": "anthropic",
       "model": "claude-sonnet-5",
       "api_key_env": "ANTHROPIC_API_KEY",
   })
   agent.write({"provider_id": provider.id, "max_steps": 12})

   run = env["ai.agent.run"].create({
       "agent_id": agent.id,
       "goal": "How many unpaid customer invoices are there, and what do they total?",
   })
   run.action_start()
   run.action_run_to_completion()
   print(run.answer)
   run.step_ids.mapped(lambda s: (s.tool_id.name, s.args, s.result))

Set a ``goal`` and the run is model-driven; leave it empty and the run
follows its ``plan`` exactly as before. Both paths share the same gates,
step records and resume cursor.

Tool schemas
------------

``tool._tool_schema()`` derives the parameter names, their JSON types
and any reST ``:param:`` text straight from the method's real signature.
The **description stays hand-written**, because that is the part
derivation cannot supply: Odoo's docstrings explain mechanics to a
developer who has already decided to call the method, not when an agent
should reach for it.

So "derive the schema or hand-write it" is a false choice — derive the
shape, write the description.

Testing without a provider
--------------------------

.. code:: python

   run = run.with_context(stub_script=[
       {"kind": "tool", "tool": "count_partners", "args": {"domain": []}},
       {"kind": "final", "answer": "42"},
   ])

A ``stub`` provider replays that list, indexed by how many steps have
happened. The script travels in the context so the stub needs no column
of its own.
